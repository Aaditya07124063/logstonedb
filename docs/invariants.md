# LogstoneDB — Invariants

> **Authorship:** generated by Claude (AI assistant) on 2026-10-10. Not written by the human operator.
> **Authorship decision:** all project material is AI-written; see ADR-015 in `docs/decisions.md`. No separate operator-authored invariant document is required.
> **Status:** draft. No invariant here is "verified" until the test IDs listed against it exist and pass.

Each property lists: **Statement** (precise), **Enforced by** (the mechanism), **Counterexample** (what breaks without the mechanism), **Evidence** (test IDs from `docs/testing.md`).

Notation: `term`, `votedFor`, `log[i]` = (index, term, data), `commitIndex`, `lastApplied`. "Committed" means: stored on a majority **and** covered by a leader's commit decision under rule R-COMMIT below.

## 1. Raft safety properties (Raft paper §5, Figure 3)

### S1 — Election Safety
**Statement.** For every term T, at most one node becomes leader in T.
**Enforced by.**
1. Each node grants at most one vote per term, and persists `(term, votedFor)` durably **before** sending the vote reply.
2. A candidate becomes leader only with votes from a majority of the 3 configured nodes.
3. Any two majorities of 3 intersect in at least one node.

**Counterexample (without durable vote).** Node B votes for A in term 6, crashes before persisting, restarts with `votedFor = none`, and votes for C in term 6. A has {A, B}, C has {C, B}: two leaders in term 6.
**Evidence.** SIM-E01, SIM-E02, SIM-E05 (vote-amnesia mutant must fail).

### S2 — Leader Append-Only
**Statement.** A leader never overwrites or deletes entries in its own log; it only appends.
**Enforced by.** The leader code path has no truncation operation. Truncation exists only in the follower path when AppendEntries conflicts.
**Counterexample.** A leader that "fixes" its own log to match a follower could delete an entry it already counted toward commitment, losing a committed write.
**Evidence.** SIM-R03 (assertion in the simulator's leader step function).

### S3 — Log Matching
**Statement.** If two logs contain an entry with the same index and term, then (a) the entries are identical, and (b) the logs are identical in all entries up to that index.
**Enforced by.**
1. A leader creates at most one entry per index in its term (S2 plus S1).
2. AppendEntries carries `(prevLogIndex, prevLogTerm)`. A follower rejects it unless its own log has an entry at `prevLogIndex` with term `prevLogTerm`.
3. On conflict (same index, different term), the follower deletes that entry and every entry after it, then appends the leader's entries.

**Counterexample (without the prev check).** Follower log `[1:t1][2:t2]`, leader log `[1:t1][2:t3][3:t3]`. Leader sends only entry 3. Without the check the follower appends it, producing `[1:t1][2:t2][3:t3]`: same (3, t3) as the leader but different prefix.
**Evidence.** SIM-R01, SIM-R02, SIM-R05 (prev-check-disabled mutant must fail).

### S4 — Leader Completeness
**Statement.** If an entry is committed in term T, it is present in the log of every leader of every term > T.
**Enforced by.**
1. R-VOTE: a voter refuses a candidate whose log is less up-to-date than its own (compare last log term; if equal, compare last log index).
2. A committed entry is on a majority; a winning candidate has votes from a majority; the two sets intersect; the intersecting voter holds the entry and refuses any candidate lacking it.
3. R-COMMIT (below), which ensures "committed" really means "protected by R-VOTE".

**Counterexample (without R-VOTE).** `x=100` is on A and B (committed, acknowledged). C lacks it. A crashes. C asks B for a vote; B grants. C becomes leader and overwrites B's entry. The acknowledged write is lost.
**Evidence.** SIM-E03, SIM-R06, Figure-8 scenario SIM-C02.

### S5 — State Machine Safety
**Statement.** If a node applies the entry at index i to its state machine, no other node ever applies a different entry at index i.
**Enforced by.** Nodes apply only entries with index ≤ their `commitIndex` (R-APPLY), in index order, exactly once per index per boot. By S4 and S3, every committed index holds the same entry everywhere.
**Counterexample (without R-APPLY).** A applies uncommitted `x=100` at index 10, then is partitioned; B commits `x=200` at index 10. A and B have applied different entries at index 10, and A's clients may have seen 100.
**Evidence.** SIM-R04, SIM-P01, DB-L* (Porcupine) campaigns.

## 2. Additional rules and system-level safety properties

### R-COMMIT — current-term commit rule
**Statement.** A leader advances `commitIndex` to N only if a majority has `matchIndex ≥ N` **and** `log[N].term == currentTerm`. Entries from earlier terms become committed only indirectly, when a later current-term entry commits (by S3).
**Counterexample (Raft paper Figure 8, 3-node form).**
1. Term 2: S1 leader, appends (2) at index 2 only on S1, crashes.
2. Term 3: S3 elected (S2 votes), appends (3) at index 2 only on S3, crashes.
3. Term 4: S1 elected, replicates (2) to S2. Entry (2) is now on a majority.
4. If S1 commits index 2 now and acknowledges, then crashes:
5. Term 5: S3 asks S2 for a vote. S3's last term 3 > S2's last term 2, so S2 grants. S3 overwrites index 2 on S2. Acknowledged write lost.

**Fix.** In step 3, S1 commits only after replicating a term-4 entry (no-op) at index 3 to S2. Then S3 cannot win.
**Evidence.** SIM-C01, SIM-C02 (old-term-commit mutant must fail).

### R-APPLY — apply only committed
**Statement.** `lastApplied ≤ commitIndex` at all times on every node; the read path reads only the state machine, never the log.
**Evidence.** Runtime assertion in simulator and in `internal/server`; SIM-R04.

### L-ACK — acknowledged-write durability
**Statement.** If a write is acknowledged to a client, then (within the fault model) every later linearizable read observes it or a later write.
**Enforced by.**
1. Acknowledge only after the entry is committed (R-COMMIT) **and** applied on the acknowledging leader.
2. Commitment counts only **durable** copies: a node reports success for an entry (AppendEntries reply, or the leader counting itself) only after the entry is synced (`docs/storage.md` W3).
3. S4 carries the entry into every future leader.

**Counterexample (ack after write but before sync).** Leader and one follower hold the entry in page cache only; the leader commits and acknowledges; both lose power. The entry exists nowhere durable.
**Evidence.** F01, F02, STO-W03, DB-CR* campaigns.

**Commit durability contract.** `HardState.Commit` does **not** need to be synced before acknowledging a client. Commitment is a property of the replicated log (durable on a majority), not of any node's local `Commit` field. A node that restarts with a stale `Commit` relearns it from the leader. (etcd/raft's `MustSync` reflects this; to be verified against the pinned version.)

### L-READ — linearizable reads
**Statement.** A successful GET returns a value that reflects every write acknowledged before the GET was invoked.
**Enforced by.** etcd/raft ReadIndex in `ReadOnlySafe` mode:
1. The leader has committed an entry in its current term.
2. `readIndex := commitIndex` recorded when the request is processed.
3. A heartbeat round **issued after** that point, tagged with the request context, is acknowledged by a majority in the leader's current term.
4. The server waits until `lastApplied ≥ readIndex`, then reads the state machine.

**Counterexample A (local read on isolated leader).** A is leader term 5 with `x=50`, partitioned. B leads term 6 and acknowledges `x=200`. A client then reads A locally: 50. Stale.
**Counterexample B (acks not tied to the request).** Heartbeat acks from before the partition arrive late; if counted for a read received after B committed `x=200`, A serves 50.
**Evidence.** F09, DB-RD01..04, Porcupine histories.

### L-DEDUP — at-most-once execution of client mutations
**Statement.** For each session `(ClientID)` and sequence number `s`, the mutation is **executed** at most once in the replicated state machine, and every response for `(ClientID, s)` returns the result of that single execution.
**Enforced by.** The session table is part of the replicated state machine, updated in the same `apply` step as the mutation, included atomically in snapshots; duplicate detection happens in `apply`, not only before proposing (`docs/protocol.md` §5).
**Counterexample.** CAS(x,10,20) commits and applies, response lost. Another client sets x=10. Retry is re-executed: x becomes 20 again, overwriting the other client's acknowledged write. No linearization explains it if any read observed 20 in between.
**Scope.** At-most-once execution plus client retries gives exactly-once **within a live session under the client contract** (`docs/assumptions.md` §5). After session expiry or client state loss, the outcome of an outstanding operation is unknown. No unconditional exactly-once claim.
**Evidence.** F07, DB-DD01..05, SIM audit counter.

### ST-1 — no silent loss on recovery
**Statement.** Recovery never produces a durable state that is missing a WAL batch which was synced before the crash, except where it fail-stops instead.
**Enforced by.** Batch framing with chained checksums, truncation only of an incomplete final batch, fail-stop on middle corruption (`docs/storage.md` §5).
**Evidence.** STO-W01..W08.

### ST-2 — no fallback to an obsolete storage generation
**Statement.** Once any action depends on storage generation G (cleanup, an acknowledgement, a snapshot install), recovery never selects a generation < G.
**Enforced by.** Two metadata slots, both written with G before any dependent action; recovery picks the highest valid generation and fail-stops if any referenced artifact is missing (`docs/storage.md` §6). Under exclusion X1 (rollback), this is not guaranteed.
**Evidence.** STO-M01..M06.

### ST-3 — snapshot consistency
**Statement.** A snapshot at index N contains exactly the state machine state (KV map, session table, logical clock) after applying entries 1..N, and recovery replays from N+1.
**Evidence.** STO-S01..S04.

### ID-1 — identity-preserving restart
**Statement.** A node with missing or empty storage never rejoins as an existing member.
**Enforced by.** Durable identity file; startup refusal (`docs/storage.md` §8).
**Evidence.** F12, DB-ID01.

## 3. Liveness properties (require T2; not guaranteed under arbitrary faults)

| ID | Statement | Conditions |
|---|---|---|
| LV1 | A leader is eventually elected. | A majority is connected and not paused for long enough (T2); randomized election timeouts; PreVote enabled. |
| LV2 | A proposed operation eventually commits or the client receives an error/timeout. | LV1 plus the leader stays connected to a majority. |
| LV3 | A linearizable read eventually completes or times out. | LV1. An isolated node never completes it (correct). |
| LV4 | A restarted follower eventually catches up (log or snapshot). | Connected to the leader; leader retains log or can send snapshot. |
| LV5 | An isolated leader steps down. | CheckQuorum enabled; election timeout elapses. |

Liveness failures are bugs only when the stated conditions hold. A test that partitions the majority and expects progress is wrong.

## 4. What these invariants do **not** claim

- They do not prove linearizability. Porcupine checks finite histories only.
- They do not hold under the exclusions in `docs/assumptions.md` §6.
- The educational simulator (`internal/raft`) demonstrates S1–S5 for its own simplified protocol. It says nothing about etcd/raft or the database.
