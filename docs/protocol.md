## 1. Client API

Transport: gRPC over TCP (proposal; plain HTTP/JSON acceptable if gRPC slows Week 7). Keys and values are opaque byte strings. Limits: key ≤ 1 KiB, value ≤ 64 KiB (proposal; enforced at the API boundary, rejected with `INVALID_ARGUMENT`).

All mutating requests carry a session header:

```
SessionHeader { client_id: uint64, seq: uint64 }   // seq ≥ 1
```

| Operation | Request | Success response | Semantics |
|---|---|---|---|
| `REGISTER` | `{}` | `{client_id}` | Creates a session through the log. `client_id` = log index of the register entry. |
| `PUT` | `{hdr, key, value}` | `{}` | Sets `key = value`. |
| `DELETE` | `{hdr, key}` | `{existed: bool}` | Removes `key`. `existed` reports whether it was present at execution time. |
| `CAS` | `{hdr, key, expected: optional bytes, new: bytes}` | `{swapped: bool, current: optional bytes}` | If current value equals `expected` (absent `expected` means "key must not exist"), set `key = new` and return `swapped=true`. Otherwise `swapped=false` and `current` = value at execution time. |
| `GET` | `{key}` | `{found: bool, value}` | Linearizable read through ReadIndex. No session needed. |
| `KEEPALIVE` | `{hdr.client_id}` | `{}` | Refreshes session activity through the log (no seq consumed). |
| `QUERY_OUTCOME` | `{client_id, seq}` | `{state: EXECUTED(resp) / NOT_EXECUTED / UNKNOWN}` | Linearizable lookup in the session table. `EXECUTED` only if `seq == LastSeq`; `NOT_EXECUTED` if `seq == LastSeq+1`; `UNKNOWN` if the session is gone. |
| `STATUS` | `{}` | `{node_id, role, term, leader_id, commit, applied, snapshot_index, storage_gen, health}` | **Local, not linearizable.** Diagnostic only. |

**Concurrency semantics.** All operations except `STATUS` are linearizable. Concurrent operations from different clients are ordered by the log. A client has at most one outstanding mutating operation per session (client contract C1); `GET` is not restricted.

## 2. Error codes

| Code | Meaning | Client action | Was the operation executed? |
|---|---|---|---|
| `OK` | Success | — | Yes, exactly once |
| `NOT_LEADER{leader_hint}` | Contacted node is not leader | Retry same request at hint or another node | No (not proposed) |
| `UNAVAILABLE` | No leader known / no quorum | Back off, retry same request | No (not proposed) |
| `TIMEOUT` | Server gave up waiting for commit/apply/read confirmation | Retry **same** `(client_id, seq)` | **Unknown** |
| `SESSION_EXPIRED` | `client_id` not in session table | Surface to application; outstanding outcome unknown; register anew | Unknown for the outstanding op |
| `SEQ_GAP` | `seq > LastSeq+1` | Client bug; do not retry blindly | No |
| `SEQ_CONFLICT` | `seq == LastSeq` with different content | Client bug | No (the earlier op with that seq stands) |
| `STALE_SEQ` | `seq < LastSeq` | Delayed duplicate; ignore | Earlier result already delivered |
| `SESSION_TABLE_FULL` | Registration refused, table at cap | Back off, retry register | No |
| `INVALID_ARGUMENT` | Malformed request, size limits | Fix request | No |
| `FAIL_STOPPED` | Node refused to serve due to storage integrity failure | Use another node; operator action | No |

The key distinction: **`TIMEOUT` means unknown, never failed.**

## 3. Routing, timeouts, retries

1. Clients know all three node addresses (static config).
2. Any node accepts requests. A follower returns `NOT_LEADER{leader_hint}` (no proposal forwarding in v1; `DisableProposalForwarding = true`, to verify exact field name).
3. Server-side deadline per request: 2 s default (config). On expiry the server returns `TIMEOUT` and **does not** attempt to cancel the proposal (it may still commit).
4. Client retry policy: exponential backoff 10 ms → 1 s, jittered, rotating nodes on `NOT_LEADER`/`UNAVAILABLE`, same `(client_id, seq, content)` on `TIMEOUT`.
5. A client may call `QUERY_OUTCOME` to resolve an ambiguous result while its session is alive.

## 4. Request flows

Boundary markers: **[D]** durable on a majority · **[C]** committed (leader knows) · **[A]** applied on the responding node · **[R]** response sent.

### 4.1 PUT / DELETE / CAS (leader)
1. Validate request; optional pre-check of session table (optimization only, see §5.4).
2. Encode command (§6), `node.Propose(ctx, data)`; register a waiter keyed by `(client_id, seq)` and the expected log position (if known) or a proposal ID embedded in the command.
3. Ready loop persists the entry, then sends AppendEntries (§8).
4. Followers persist, reply success. **[D]** when a majority (including leader's own durable copy) has it.
5. etcd/raft advances commit (current-term rule). **[C]**
6. Entry appears in `CommittedEntries`; state machine `apply` executes it (or returns cached response). **[A]**
7. Waiter matched by `(client_id, seq)` receives the apply result. **[R]**

If leadership is lost before step 7, all waiters fail with `TIMEOUT` (outcome unknown).

### 4.2 GET (ReadIndex)
1. Generate a unique request context `rctx` (16 random bytes or counter + node ID).
2. `node.ReadIndex(ctx, rctx)`.
3. Wait for a `ReadState{Index, RequestCtx == rctx}` in `Ready.ReadStates`.
4. Wait until `lastApplied ≥ Index`.
5. Read the state machine. **[R]**
6. On deadline: `TIMEOUT`. On leadership loss: `NOT_LEADER`. Never fall back to a local read.

etcd/raft internally rejects ReadIndex until the leader has committed an entry in its current term (to verify against pinned version; if not, the adapter enforces it by checking `Status().Commit` against the term of the leader's first entry).

### 4.3 REGISTER
Propose `RegisterClient`; on apply, `client_id = entry index`. Response after **[A]**.

## 5. Sessions and deduplication

### 5.1 Session record (part of replicated state, snapshotted with KV)

```
Session {
  client_id   uint64      // index of RegisterClient entry; never reused
  last_seq    uint64      // 0 = none executed yet
  last_digest [16]byte    // trunc. SHA-256 of canonical op encoding at last_seq
  last_resp   Response    // original result, returned verbatim on duplicates
  last_active uint64      // logical time (ms) of last accepted entry
}
StateMachine { kv, sessions map[uint64]Session, logical_now uint64, applied_index uint64 }
```

### 5.2 Deterministic apply rules (evaluated in log order on every replica)

```
apply(entry e):
  logical_now = max(logical_now, e.leader_ts)
  expire sessions with last_active + TTL < logical_now          // §5.5
  switch e.cmd:
  RegisterClient:
      if len(sessions) >= CAP: return SESSION_TABLE_FULL
      sessions[e.index] = {client_id: e.index, last_seq: 0, last_active: logical_now}
      return Registered(e.index)
  KeepAlive(c):
      if c in sessions: sessions[c].last_active = logical_now; return OK
      return SESSION_EXPIRED
  Mutation(c, s, op):
      S, ok = sessions[c]
      if !ok:                         return SESSION_EXPIRED
      if s == 0:                      return INVALID_ARGUMENT
      d = digest(op)
      if s == S.last_seq:
          if d == S.last_digest:      S.last_active = logical_now; return S.last_resp
          else:                       return SEQ_CONFLICT
      if s <  S.last_seq:             return STALE_SEQ
      if s >  S.last_seq + 1:         return SEQ_GAP
      r = execute(op)                 // s == last_seq + 1
      sessions[c] = {c, s, d, r, logical_now}
      return r
```

Rejections never modify the session and are never cached.

### 5.3 Case table

| Case | Result |
|---|---|
| First request after register | `seq` must be 1 → executes |
| Duplicate, identical content | Cached original response, not executed |
| Same seq, different content | `SEQ_CONFLICT` |
| Gap (`seq > last+1`) | `SEQ_GAP` |
| Old seq (`seq < last`) | `STALE_SEQ` |
| Unknown / expired session | `SESSION_EXPIRED`, never auto-created |
| Retry after ambiguous timeout | Same `(c, s, content)` → executes once, later copies get cached response |
| Retry arriving before original is applied (both in log) | First copy executes, second gets cached response |
| Client restarts with persisted `(c, last_seq)` | Resumes; retries outstanding op |
| Client restarts without persisted state | Must register anew; old outcome via `QUERY_OUTCOME` if old ID known, else unknown |

### 5.4 Pre-proposal check
The leader may reject obvious duplicates before proposing (e.g. return cached response if `s == last_seq` and digest matches **and** the leader's applied index covers the session's latest update). This is an optimization. Correctness relies only on §5.2.

### 5.5 Expiry and capacity (deterministic)
- `TTL` default 1 hour of logical time; `CAP` default 10,000 sessions (config, identical on all nodes; part of cluster config file checked at startup).
- Expiry uses only `logical_now`, a max over leader timestamps in the log, so all replicas expire identical sessions at identical indices.
- **At capacity, new registrations are refused** (`SESSION_TABLE_FULL`). Live sessions are never evicted to make room (addresses Round 3 finding 3).
- A leader with a fast clock can expire sessions early: affects availability of deduplication, not safety. Documented in `docs/assumptions.md` T4.

### 5.6 Guarantee statement
The system provides **at-most-once execution of committed mutations per `(client_id, seq)`**, and, combined with client retries under contract C1–C3, exactly-once logical application **while the session is alive**. It does not guarantee outcome discovery after session expiry, and it says nothing about external side effects a client performs.

## 6. State-machine command encoding

```
Command {
  version   uint8          // = 1
  kind      uint8          // REGISTER, KEEPALIVE, PUT, DELETE, CAS, NOOP
  client_id uint64
  seq       uint64
  leader_ts uint64         // ms, stamped by the proposing leader
  key, value, expected, has_expected
}
```
Canonical encoding (fixed field order, little-endian, length-prefixed bytes) is used both on the wire and for `digest`. `leader_ts` is excluded from the digest so retries proposed by different leaders match. Unknown `version` → fail-stop on apply (cannot be applied deterministically).

## 7. Peer transport

- Carries `raftpb.Message` values between the three nodes. Framing: `[len u32][crc32c u32][protobuf bytes]` over a long-lived TCP connection per peer pair (proposal).
- No ordering or delivery guarantee is relied on (Raft tolerates N1–N4).
- On send failure: `node.ReportUnreachable(to)`.
- `MsgSnap`: streamed; on completion or failure call `node.ReportSnapshot(to, status)`.
- Bounded per-peer send queue; overflow drops messages (safe for Raft).
- Every message from an unknown node ID or a different cluster ID is dropped.

## 8. etcd/raft integration contract (Ready / Advance)

Source checked: `github.com/etcd-io/raft` README, fetched 2026-10-10 (module `go.etcd.io/raft/v3`). Exact version-specific behaviour **must be re-verified** against the version pinned at Milestone 6 and recorded in `docs/decisions.md` ADR-003.

What the README states (paraphrased):
- Persist Entries, then HardState and Snapshot (if non-empty). When writing an entry at index i, discard previously persisted entries with index ≥ i.
- Do not send Messages until the latest HardState and all Entries from **previous** Ready batches are persisted; messages may be sent while the same batch's entries are being persisted. Leader parallel writes are an allowed optimization (thesis §10.2.1).
- Apply Snapshot and CommittedEntries; call `Advance()` after step 1; process Ready batches in order.

**LogstoneDB v1 contract (deliberately stricter than the library minimum):**

```
for each rd := <-node.Ready():
  1. storage.SaveBatch(rd.Entries, rd.HardState, rd.Snapshot)   // one WAL batch
     if rd.MustSync (or rd.Snapshot non-empty): fsync before continuing
     mirror into raft.MemoryStorage (ApplySnapshot / SetHardState / Append)
  2. transport.Send(rd.Messages)          // ONLY after step 1 returned
  3. if snapshot: sm.Restore(rd.Snapshot); applyIndex = snapshot.Index
     for e in rd.CommittedEntries: sm.Apply(e) (NOOP/empty → advance index only)
  4. resolve ReadStates waiters whose index ≤ applied
  5. node.Advance()
```

- **No parallel leader writes in v1**: simplest argument that a node counts itself only once durable. Revisit only in Week 23 with a regression test.
- Term and vote are persisted (step 1) before any vote reply leaves (step 2). This is what S1 relies on.
- `HardState.Commit` changes alone do not force fsync (`MustSync` false); see L-ACK commit durability contract.
- Configuration: `CheckQuorum = true`, `PreVote = true`, `ReadOnlyOption = ReadOnlySafe`, `ElectionTick = 10`, `HeartbeatTick = 1`, tick interval 100 ms (proposal), `MaxSizePerMsg` and `MaxInflightMsgs` tuned in Week 21.
- Restart: load storage (`docs/storage.md` §7), populate `MemoryStorage`, set `Config.Applied = snapshot.Index` (in-memory state machine is rebuilt by replaying committed entries above the snapshot), `RestartNode`.
