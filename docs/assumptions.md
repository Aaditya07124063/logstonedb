# LogstoneDB — Assumptions, Failure Model and Exclusions

> **Authorship:** generated by Claude (AI assistant) on 2026-10-10 from the LogstoneDB master prompt and prior review rounds. Not written by the human operator.
> **Status:** draft for architecture review. Nothing here has been verified by executing code.

This file defines the world LogstoneDB is designed for. Every safety claim in `docs/invariants.md` holds **only inside this model**. Anything outside it is either an explicit exclusion (§6) or an open question (§8).

---

## 1. System shape

| Item | Assumption |
|---|---|
| Cluster | Exactly 3 nodes, fixed membership, single shard |
| Quorum | 2 of the 3 configured nodes (not of the reachable nodes) |
| Node identity | Each node has a permanent, unique, non-zero Raft ID (1, 2, 3), never reused |
| Storage ownership | Each node exclusively owns one local data directory; no two processes ever open the same directory |
| Language / runtime | Go (version pinned in `go.mod`; exact version to be recorded at Milestone 0) |
| Consensus library | `go.etcd.io/raft/v3` for the networked database (exact version pinned and recorded at integration time) |
| Educational simulator | Independent code in `internal/raft`; never used by the database |

## 2. Process and network failure model

**Allowed failures (the system must stay safe under any combination of these):**

| ID | Failure | Notes |
|---|---|---|
| N1 | Message loss | Any message may be dropped |
| N2 | Message delay | Unbounded, arbitrary delay |
| N3 | Message duplication | Any message may be delivered more than once |
| N4 | Message reordering | Between any pair of nodes, in any direction |
| N5 | Network partition | Any split, symmetric or asymmetric, healing at any time |
| P1 | Process crash (crash-stop) | All volatile state lost; durable state per §3 retained |
| P2 | Process restart (crash-recovery) | Node restarts with its durable state and the same identity |
| P3 | Process pause | Arbitrary pause (GC, SIGSTOP, VM suspend) at any instruction |
| P4 | Machine power loss | Equivalent to P1 plus loss of unsynced storage bytes per §3 |

**Not allowed (outside the model):**

- Byzantine behaviour: nodes or clients lying, forging messages, or running modified code.
- Message corruption that passes checksums undetected. (Transport frames carry a checksum; TCP is not trusted for this alone.)
- Two processes running with the same node ID at the same time.

## 3. Storage contract

The storage contract is the most important assumption in the project. It is stated as rules here and will later be enforced by an executable fake filesystem (`docs/storage.md` §10, used by `docs/testing.md` §5).

| ID | Rule |
|---|---|
| S1 | Bytes covered by a `fsync`/`fdatasync` that **returned success** survive any later crash or power loss, unchanged. |
| S2 | Bytes written but **not yet covered** by a successful sync may, after a crash, be: fully present, fully absent, partially present in any subset of sectors, replaced by zeros, or replaced by stale contents. **Unsynced data is never assumed absent.** A complete unsynced batch may survive. |
| S3 | A newly created file, a rename, or an unlink is durable only after the **parent directory** has been synced successfully. Before that, after a crash the directory may show the old or the new state. |
| S4 | A rename of one file over another is atomic: after a crash the name refers to either the old file or the new file, never a mixture. |
| S5 | A sync that returns an error leaves the durability of all unsynced data **unknown**, and a later sync on the same file may falsely succeed. Therefore any sync error causes the node to fail-stop (see `docs/storage.md` §9). |
| S6 | The device honours cache-flush commands. On macOS this requires `F_FULLFSYNC`; plain `fsync` there is not sufficient. (Go's `os.File.Sync` behaviour on darwin to be **verified** against the pinned Go version.) |
| S7 | Media corruption (bit rot) of synced data is possible but rare. It is **detected** by checksums and handled by fail-stop. It is not silently repaired. |

**Primary target platform:** Linux, ext4 or xfs, local SSD. macOS is a development platform only; durability tests that rely on real-filesystem behaviour are run on Linux. Behaviour on network filesystems is out of scope.

## 4. Timing assumptions

| ID | Assumption | Used for |
|---|---|---|
| T1 | **None** for safety. | All safety properties hold in a fully asynchronous network (Raft's design). |
| T2 | Partial synchrony: eventually, messages between a majority of nodes are delivered within a bound much smaller than the election timeout, and those nodes are not paused. | Liveness only (`docs/invariants.md` §3). |
| T3 | Each node has a monotonic clock used only for ticking Raft timers and for local timeouts. | Liveness only. |
| T4 | Leader wall-clock timestamps written into log entries are used only for **deterministic session expiry**. Clock error can make sessions expire early or late, which affects availability of deduplication, never safety. | Sessions (`docs/protocol.md` §5). |

**Lease-based reads are not used** in v1, because they would make safety depend on timing assumptions that this model does not make (ADR-004 in `docs/decisions.md`).

## 5. Client assumptions

| ID | Assumption |
|---|---|
| C1 | A client has at most one outstanding operation per session. |
| C2 | A client retries an operation with byte-identical content and the same `(ClientID, Seq)` until it gets a definitive response or `SESSION_EXPIRED`. |
| C3 | A client reuses a `ClientID` only if it has durably remembered its `LastSeq`. Otherwise it registers a new session. |
| C4 | Clients are not Byzantine, but may be buggy. Protocol violations (gaps, conflicting content for one seq) are rejected deterministically, not trusted. |
| C5 | Clients may crash, time out, and reconnect to any node at any time. |

## 6. Explicit exclusions (outside the v1 fault model)

| ID | Exclusion | What the system does if it happens anyway |
|---|---|---|
| X1 | **Arbitrary rollback of previously durable storage** (restoring an old disk image, snapshot, or backup of a data directory). | Not detected in general. Artifact validation and generation checks catch *some* cases and fail-stop. **No claim is made to detect every rollback.** Running a rolled-back node can violate safety. |
| X2 | **Permanent loss of a majority's durable storage** (2 of 3 disks destroyed). | Acknowledged writes may be unrecoverable. Nodes with empty storage refuse to start as existing members. The cluster reports itself unavailable. Recovery is only by an explicit, operator-invoked unsafe procedure that documents the possible data loss. |
| X3 | Storage devices that acknowledge a flush without making data durable (lying firmware). | Can violate durability. Out of scope; documented, not mitigated. |
| X4 | Byzantine nodes or clients. | Out of scope. |
| X5 | Membership changes (adding, removing, replacing nodes). | Not supported. A node that lost its storage cannot be safely replaced in v1; the cluster continues with the remaining two and zero further fault tolerance. |
| X6 | Undetected memory corruption, CPU faults, Go runtime bugs. | Out of scope. |

## 7. Non-goals for v1

SQL; transactions across keys; sharding or multi-Raft; dynamic membership; cross-region deployment; TLS, authentication, authorization; a graphical dashboard; production operations tooling; a production-quality custom Raft implementation; formal proof of correctness.
