## 1. Data directory layout

```
data/
  IDENTITY              cluster_id, node_id, created_at, crc        (write-once)
  META-A, META-B        storage-generation authority (two slots)     §6
  snap/
    snap-<gen>-<index>-<term>.snap                                    §4
  wal/
    wal-<segSeq>-<firstIndex>.log                                     §3
  *.tmp                 in-progress files; never loaded
```

## 2. What is durable and why

| Item | Where | Why durable |
|---|---|---|
| Log entries | WAL | Counted toward majorities (S4, L-ACK) |
| HardState `{Term, Vote, Commit}` | WAL record (same batch as entries) | Term/Vote for S1. Commit is a lower bound only; durability of Commit is not required for safety |
| Snapshot (KV + sessions + logical clock + index/term + membership) | snapshot file | Allows log compaction; must include sessions (L-DEDUP) |
| Live generation (which snapshot, which segments, wal floor) | META-A/B | Single authority for recovery (ST-2) |
| Node identity | IDENTITY | ID-1 |

The state machine itself is **in memory** in v1 and rebuilt from snapshot + WAL replay on every start.

## 3. WAL format — PROVISIONAL

### 3.1 Segment header
```
{ magic "LSDBWAL1", version u16, seg_seq u64, first_index u64,
  created_gen u64, cluster_id u64, node_id u64, header_crc u32 }
```
Segments rotate at 64 MiB (config). A new segment becomes live only when a metadata generation that references it is published (§6).

### 3.2 Record
```
{ len u32 | type u8 | crc u32 | payload [len]byte }
crc = CRC32C(prev_crc ‖ len ‖ type ‖ payload)        // chained; first record seeds from header_crc
types: ENTRY, HARDSTATE, TRUNCATE_SUFFIX{from_index}, SNAPSHOT_MARK{index,term}, COMMIT
```
- `len` bounded: `len ≤ MaxRecord (4 MiB)` and `≤ bytes remaining`; violation = invalid record.
- CRC covers the length and type, so a corrupted length cannot silently re-frame the stream.

### 3.3 Batch
A batch is the unit of atomicity and corresponds to one `Ready` persistence step:
```
[records ...][COMMIT{batch_seq u64, record_count u32, chain_crc u32, standalone_crc u32}]
```
`standalone_crc` covers `(batch_seq, record_count, chain_crc)` only, so a COMMIT can be recognized by a forward scan without the chain (used for corruption detection, §5.2).

### 3.4 Writer ordering rules
| Rule | Statement |
|---|---|
| W1 | One writer goroutine. A batch is written as records then COMMIT, then synced. |
| W2 | No byte of batch k+1 is written until the sync of batch k has returned success. No pipelining across this barrier. |
| W3 | Nothing externally visible that depends on batch k (any message, vote, AppendEntries reply, client response, metadata publication referencing it) happens before batch k's sync returns. |
| W4 | Before writing, the writer asserts the batch leaves a consistent state: `HS.Term ≥ last entry term`; `HS.Commit ≤ last index` (or snapshot index); `TRUNCATE_SUFFIX.from > HS.Commit` and `> snapshot index`. Violation = bug = fail-stop. |
| W5 | Any sync error = fail-stop immediately (S5). No retry. |

### 3.5 Conflicting-suffix replacement
When `Ready.Entries` begins at index i ≤ current last index, the storage layer writes, **in one batch**, `TRUNCATE_SUFFIX{from=i}` followed by the new entries. Nothing is overwritten in place. Readers apply records in order: TRUNCATE drops in-memory entries ≥ i.

## 4. Snapshot format — PROVISIONAL

```
header { magic, version, gen, index, term, conf_state, body_len, body_crc, header_crc }
body   { logical_now, applied_index (== index), kv entries (sorted), sessions (sorted) }
footer { magic }
```
- Written from a **consistent cut** taken in the apply goroutine at exactly `applied_index` (copy or copy-on-write; no apply runs during capture).
- Index and state are covered by one CRC; they cannot diverge.
- Sorted encoding makes snapshots of identical states byte-identical across replicas (used by tests).

## 5. WAL recovery — PROVISIONAL

### 5.1 Definition of the recoverable prefix
The longest sequence of complete batches (valid COMMIT, matching record count, unbroken CRC chain) from the start of the first live segment.

### 5.2 Algorithm
```
for each live segment in metadata order:
    verify header (magic, crc, node_id, cluster_id); mismatch → FAIL-STOP
    scan batches; at first failure at offset F (batch started at B):
        if this is not the last live segment                      → FAIL-STOP (middle corruption)
        if forward scan finds a valid COMMIT (standalone_crc) with
           batch_seq > last good batch_seq after F                 → FAIL-STOP (durable data beyond damage)
        else                                                       → torn tail: ftruncate(B); fsync(file)
replay retained records in order (ENTRY / TRUNCATE_SUFFIX / HARDSTATE / SNAPSHOT_MARK)
check invariants I1–I9 (§7)
```

### 5.3 Case table

| Case | Outcome | Reason |
|---|---|---|
| Torn final record / incomplete final batch | **Truncate** to start of that batch, proceed | Under S1 a synced batch is never torn, so this batch's sync did not return; by W3 nothing depended on it |
| Complete final batch whose sync never returned (S2: survived anyway) | **Keep**, proceed | Keeping un-acknowledged but internally valid state is equivalent to "sync returned, crashed before W3 actions": safe. Retained vote is more restrictive, not less |
| Corrupted record in a non-final segment | **Fail-stop** | Middle data was synced (W2) and may have been acknowledged |
| Corrupted record inside a batch that has a valid COMMIT | **Fail-stop** | Batch was complete; damage is media corruption (S7) |
| Valid later COMMIT found after damage | **Fail-stop** | By W2 the damaged batch was synced |
| Entry persisted, later HardState update incomplete (same batch) | **Discard whole batch** including the entry | Batch atomicity; batch never reached W3 |
| Entry persisted in batch k, HardState torn in batch k+1 | **Keep batch k**, drop k+1, use previous HardState | Retained state = a state the writer held after a successful sync (W4-checked) |
| Recovered `Commit` > last recovered index (and > snapshot index) | **Fail-stop** | Impossible under W2+W4 without storage loss or a bug |
| Crash during suffix replacement, COMMIT not durable | **Discard batch**, old suffix remains | Old entries were uncommitted; new ones never acknowledged; leader resends |
| Suffix replacement durable, ack to leader lost | **Keep replacement** | Batch complete; leader learns on next AppendEntries |
| `TRUNCATE_SUFFIX.from ≤ Commit` found | **Fail-stop** | Would delete committed entries; bug |

### 5.4 Known limitation (accepted for v1)
If media corruption destroys the end of the final segment **and** every later COMMIT, it is indistinguishable from a torn tail; recovery would truncate synced batches. Detecting this needs a separately durable high-water mark (an extra sync per batch). Treated as outside S1/S7 for v1 and listed as risk R7.

## 6. Storage generations and metadata authority — PROVISIONAL

### 6.1 Metadata slot
```
META-{A,B} = { gen u64, snapshot{file, index, term, body_crc} | none,
               wal_floor u64 (= snapshot.index + 1, or 1),
               segments [{file, seg_seq, first_index}], crc u32 }
```
Each slot is replaced by write tmp → fsync → rename → fsync dir (S3, S4), so a slot is never torn; CRC detects later corruption.

### 6.2 Publication of generation G+1 (both slots currently hold G)
```
1. Create and sync all new artifacts (snapshot, new segment) with created_gen = G+1; fsync dir.
2. Replace META-A with G+1.
3. Replace META-B with G+1.
   ── COMMIT POINT: both slots hold G+1 ──
4. Only now: cleanup of artifacts unreferenced by G+1; acknowledge an installed snapshot
   to the leader; append into a newly listed segment.
```
**Invariant P:** no action depends on generation G+1 before step 3 completes.

### 6.3 Recovery choice
1. Read both slots. `active` = valid slot with the highest gen. Neither valid → FAIL-STOP.
2. Every artifact referenced by `active` must exist and validate. Otherwise FAIL-STOP. **Never fall back to a lower generation.**
3. Orphans: non-tmp artifact with `created_gen == active + 1` = leftover of an interrupted publication → delete after successful recovery. `created_gen > active + 1` → FAIL-STOP.
4. Delete unreferenced artifacts only after all checks in §7 pass.

### 6.4 Slot-state analysis

| Slots found | How reached | Choice | Why safe |
|---|---|---|---|
| {G, G} | Before step 2 | G | G+1 not committed; its artifacts are orphans |
| {G+1, G} | Crash between steps 2 and 3 | G+1 | Nothing depended on G+1 yet; G's artifacts still exist; both choices safe |
| {corrupt, G} | Step 2 interrupted, or slot A rotted before step 3 | G | By P nothing depended on G+1; cleanup did not run |
| {G+1, G+1} | Published | G+1 | — |
| {G+1, corrupt} or {corrupt, G+1} | Published, one slot later rotted | G+1 from survivor | No loss |
| {corrupt, corrupt} | Both copies lost after publication | FAIL-STOP | Storage loss of authority; node treated as storage-failed (ID-1) |

**Property:** after publication of G+1, no slot holds G. An obsolete generation therefore cannot coexist with a published newer one. A slot holding an older generation can only reappear through storage rollback (X1), which is excluded; in that case step 2 or step 3 of §6.3 catches *some* cases (missing artifacts, orphans with newer gen) but not all.

### 6.5 Snapshot and compaction
1. Precondition: `applied ≥ N` and the durable HardState `Commit ≥ N` (true by construction: only durably-known committed entries are applied).
2. Capture consistent cut at N; write snapshot with `created_gen = G+1`; sync file and dir.
3. Publish G+1 with `snapshot = N`, `wal_floor = N+1`, segments = those containing any index ≥ N+1.
4. Cleanup: delete old snapshot and segments whose last index ≤ N (whole files only; never truncate the front of a segment).
5. Tell `MemoryStorage.Compact(N)` only after step 3.

A **follower installing a snapshot from the leader** at index N: if its log contains (N, term) keep the suffix; otherwise the new generation lists a fresh empty segment starting at N+1. The snapshot is acknowledged to Raft (via `Advance` / message reply) only after step 3 (Invariant P).

## 7. Startup invariants

| # | Check | On failure |
|---|---|---|
| I0 | IDENTITY exists, CRC valid, matches configured node_id and cluster_id | Refuse to start (ID-1) |
| I1 | Active metadata chosen per §6.3; all referenced artifacts present and valid | Fail-stop |
| I2 | `wal_floor == snapshot.index + 1` (or 1 with no snapshot) | Fail-stop |
| I3 | After TRUNCATE handling, entries contiguous from `wal_floor` to last index | Fail-stop (except torn tail §5) |
| I4 | If WAL contains `snapshot.index`, its term == `snapshot.term` | Fail-stop |
| I5 | `HS.Term ≥ snapshot.term` and `HS.Term ≥ last log term` | Fail-stop |
| I6 | `commit = max(HS.Commit, snapshot.index)`; `commit ≤ max(last index, snapshot.index)` | Fail-stop |
| I7 | Replay starts at exactly `snapshot.index + 1`; each applied index == previous + 1 | Fail-stop |
| I8 | Snapshot header gen ≤ active gen; segment created_gen ≤ active gen + 1 | Fail-stop |
| I9 | Cleanup of unreferenced files only after I0–I8 pass | — |

## 8. Identity and bootstrap
- `logstonedb bootstrap --cluster-id X --node-id N` creates IDENTITY, empty WAL segment, META-A/B gen 1. Refuses if the directory is non-empty.
- `logstonedb start` requires IDENTITY. **Empty or missing data directory → refuse to start** with a message that the node must not rejoin as an existing member.
- `logstonedb unsafe-recover --from-node N` (Week 16+, optional): offline procedure to rebuild a cluster from one survivor's state after majority storage loss (X2). Prints and logs that acknowledged writes may be lost. Never automatic.

## 9. Error handling

| Event | Behaviour |
|---|---|
| fsync / fdatasync error | Fail-stop immediately; exit non-zero; do not send pending messages |
| write error (ENOSPC, EIO) | Fail-stop |
| Checksum failure during normal reads (e.g. serving entries to a follower) | Fail-stop |
| Any startup invariant failure | Refuse to start; report via log and `STATUS` = `FAIL_STOPPED` if the process can stay up in diagnostic mode |

"Fail-stop" = stop participating in Raft and stop serving clients. The node never acknowledges anything after the first storage error.

## 10. Fake filesystem: the executable storage contract (built in Weeks 3 and 14–16, not Days 1–2)

Interface used by all storage code:
```
type FS interface { Create, OpenAppend, Open, Rename, Remove, ReadDir, MkdirAll,
                    SyncFile(f), SyncDir(path) }
```
`fakefs` behaviour:
- Tracks per file: synced bytes and unsynced bytes; per directory: synced and unsynced entries.
- `Crash(rng)`: keeps all synced bytes; for unsynced bytes chooses per 512-byte sector (seeded): keep, drop, zero, or garbage. Unsynced directory operations: each independently applied or not (renames atomic).
- Injectable errors on any call, by name and count.
- Every decision recorded in the test trace; replay by seed.

**Limitations (stated, not hidden):** the fake model does not reproduce real filesystem quirks (ext4 delayed allocation, journaling modes, reordering across files beyond the model, firmware behaviour). Passing fakefs tests does not prove real-disk durability. Week 16 optionally adds LazyFS-based runs on Linux to narrow this gap.
