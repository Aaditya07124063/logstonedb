### ADR-001 — Go as the implementation language
- **Decision:** Go, version pinned in `go.mod`.
- **Rejected:** Rust (viable, but async Rust plus ownership across concurrent components adds risk for a solo 24-week project).
- **Consequences:** use `-race` in CI; avoid map iteration order in deterministic code.
- **Status:** Agreed (challenge document recommendation).

### ADR-002 — Educational simulator separate from production consensus
- **Decision:** `internal/raft` is an independently coded, simplified Raft for learning and simulation. The database uses etcd/raft via `internal/consensus`. No import between them.
- **Rejected:** building the database on the custom Raft (unverified; irresponsible to treat as safe).
- **Status:** Agreed.

### ADR-003 — etcd/raft library and version
- **Decision:** `go.etcd.io/raft/v3`, exact version pinned at Milestone 6 (Week 6) and recorded here with the date and the README/godoc sections re-read.
- **Verified so far:** README of `github.com/etcd-io/raft` fetched 2026-10-10 (Ready ordering, MsgSnap/ReportSnapshot, MemoryStorage restart pattern, node IDs never reused).
- **To verify at pin time:** `MustSync` semantics; ReadIndex behaviour before current-term commit; `DisableProposalForwarding` field; `AsyncStorageWrites` (not used).
- **Status:** Proposed (version TBD).

### ADR-004 — ReadIndex (ReadOnlySafe), no lease reads
- **Decision:** linearizable reads only via ReadIndex in `ReadOnlySafe` mode.
- **Rejected:** lease-based reads. Safe only under bounded clock-rate drift, suspension-aware clocks, followers honouring the lease across restarts, and lease checked after reading state. The v1 fault model (`docs/assumptions.md` T1) makes none of these assumptions.
- **Consequences:** one heartbeat round per read batch; isolated leaders cannot serve reads (correct).
- **Status:** Agreed.

### ADR-005 — Custom WAL instead of etcd's `server/storage/wal`
- **Decision:** write a small custom WAL behind an `FS` interface.
- **Reason:** full control for fault injection with fakefs; batch framing and recovery rules are part of what the project must demonstrate.
- **Rejected:** etcd's WAL package (mature, but pulls in etcd server dependencies and hides the recovery logic the project is evaluated on).
- **Risk:** custom WAL bugs (R3). Mitigation: STO-W suite, mutation tests.
- **Status:** Proposed.

### ADR-006 — HardState stored as WAL records in the same batch as entries
- **Decision:** no separate HardState file.
- **Reason:** removes an independently persisted structure that could disagree with the log (Round 3 finding).
- **Status:** Proposed.

### ADR-007 — Two metadata slots, both written before acting
- **Decision:** META-A and META-B both receive generation G+1 before any action depends on G+1. Recovery picks the highest valid generation and never falls back if referenced artifacts are missing.
- **Rejected:** (a) numbered manifest files with "highest valid wins" (unsafe after cleanup: Round 3 Critical 2); (b) ping-pong slots plus a superblock pointer (leaves the obsolete generation in the other slot; fallback after rot is unsafe unless the pointer is authoritative and itself redundant).
- **Consequences:** two extra file syncs per publication (rare: segment rotation and snapshots).
- **Status:** Proposed (provisional; see `docs/storage.md` §6).

### ADR-008 — Replicated sessions, server-assigned IDs, strict sequencing
- **Decision:** `client_id` = log index of the register entry; one outstanding op per client; `seq == last_seq + 1` required; digest check; cached original response; deterministic expiry by log time; refuse registration at capacity rather than evict.
- **Rejected:** client-chosen IDs (collision and reuse problems); multiple outstanding ops with a response window (more state, more cases, not needed for v1); LRU eviction at capacity (lets unrelated clients destroy live sessions: Round 3 finding 3).
- **Status:** Agreed in direction (Round 3: "mostly sound"); details Proposed.

### ADR-009 — In-memory state machine plus snapshots
- **Decision:** KV and sessions in memory; durability via WAL and snapshots.
- **Rejected:** embedded engine (bbolt/pebble) in v1: debugging storage engine and consensus at once.
- **Consequence:** dataset must fit in memory; restart time grows with log length until snapshot.
- **Status:** Agreed (challenge document).

### ADR-010 — Arbitrary storage rollback excluded
- **Decision:** out of fault model; partial detection only; no claim to detect all.
- **Status:** Agreed (evaluator final decision).

### ADR-011 — CheckQuorum and PreVote enabled
- **Decision:** both on. Liveness/robustness, not safety.
- **Status:** Proposed.

### ADR-012 — Fail-stop on any storage error
- **Decision:** any write/sync error or integrity failure stops the node from participating. No retries of fsync.
- **Reason:** after a failed fsync, durability of unsynced data is unknown and later syncs may falsely succeed.
- **Status:** Proposed.

### ADR-013 — Conservative Ready ordering
- **Decision:** persist (and sync when required) before sending any message from the same Ready; no leader parallel disk write in v1.
- **Reason:** simplest argument that every counted copy is durable. The library permits more; v1 does not use it.
- **Revisit:** Week 23, only with regression evidence.
- **Status:** Proposed.

### ADR-014 — No proposal forwarding
- **Decision:** followers return `NOT_LEADER{hint}`; clients retry at the leader.
- **Reason:** keeps request ownership and waiters on one node; simpler ambiguity semantics.
- **Status:** Proposed.

## Change-control process
1. Any change to a safety contract (`docs/invariants.md`, `docs/assumptions.md`, `docs/storage.md`, `docs/protocol.md` §5 and §8) requires a new or amended ADR with status `Proposed`.
2. The ADR states the old rule, the new rule, which invariants and tests it affects, and the regression test added.
3. The evaluator reviews it; status changes to `Agreed` only after review.
4. Code implementing the change lands only after (3), together with its regression test.
5. Every review finding goes into `docs/review-log.md` with its resolution and the commit that resolved it.
6. No silent scope expansion: any feature not in the architecture needs an ADR first.
